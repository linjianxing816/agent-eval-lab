# Agent 评测任务生成与质量验证

[![test](https://github.com/linjianxing816/agent-eval-lab/actions/workflows/test.yml/badge.svg)](https://github.com/linjianxing816/agent-eval-lab/actions/workflows/test.yml)

让 LLM 生成 Agent 评测任务，然后**验证这些任务本身能不能用**，最后用合格的题去评测 Agent。

不是"用任务集测模型"，是"**测任务集**"。

`Python/FastAPI + SQLite + Function Calling + SSE 流式 + 多模型适配`

```
两个模型 × 90 次执行，同一套 30 条任务

               通过率      红线违规率（越权 / 执行）
deepseek-flash  0.878        3.3%
Qwen2.5-7B      0.558       12.8%
─────────────────────────────────────────
差              32.0pp       9.5pp
门槛            12.7pp       8.1pp     → 两个维度都能区分

32 并发跑 420 次，加速 25.21×，429 为 0
```

**这组数字是修完 23 条坏题之后才成立的。** 修之前是反向的（7B 反而"更好"）。

---

## 为什么做

人工写 Agent 测试任务太慢，LLM 一分钟能出 100 条。但质量不可控——**而且坏题不会随机分布**。

实测：100 条里 17 条有硬伤。其中一类是「期望值违反业务规则」（非 VIP 用户却断言全额退款）——这类题会让**算得对的模型失败、不查就做的模型通过**。

```
修前  deepseek 0.678 / Qwen 7B 0.742  → "7B 更强"
修后  deepseek 0.878 / Qwen 7B 0.558  → "deepseek 强 32pp"
```

**同一批任务、同一批模型、同一个判定层，只有 23 条任务的期望值变了，结论完全反向。**

这就是"必须先验证评测集"的理由。

## 三个技术点

### ① 三层判定

```
结果层   success_criteria 全部满足？
过程层   有没有越权 / 循环 / 提前声称完成？
效率层   步数 / token / 耗时
```

**关键设计：过程违规分红线黄线。**

| | 判什么 | 判定 |
|---|---|---|
| 红线 | 越权 `forbidden_tool`、提前声称完成 `premature_finish` | 失败 |
| 黄线 | 超步数、循环 | 通过，记警告 |

**理由**：`max_steps` 是人为限制，不是业务规则——多走两步是"笨"不是"坏"。但越权在真实系统里是事故。

**这层能抓到单轮评测抓不到的东西**：结果对，但中途调了不该调的工具。

### ② 四维质检

| 维度 | 判什么 | 门槛 |
|---|---|---|
| 可执行性 | 格式合法、能跑完 | 100% |
| 可判定性 | 同题跑 3 次，判定是否一致 | ≥ 90% |
| 正确性 | 期望值本身对不对 | ≥ 80% |
| 区分度 | 能不能分出好坏系统 | 由样本量定 |

前三关是"题对不对"，第四关是"题有没有用"。

**第四关需要一个"明显更差"的参照物**——只用同一模型删工具做对照时，缺信息 ≠ 能力弱（模型会绕路或变保守），两个反向效应互相抵消，测不出区分度。

### ③ 门槛由样本量推，不拍脑袋

```
门槛 = 2 × sqrt(p₁(1−p₁)/n + p₂(1−p₂)/n)
```

**这是两个比例之差的标准误。** 早期版本误用单比例公式，偏松 √2 倍（0.0765 vs 0.1056），差点让一个不该过的门禁通过。

## 三个发现

### ① 坏题不会随机分布，它们系统性偏袒某一类模型

| 坏题类型 | 偏袒谁 |
|---|---|
| 期望值违反业务规则（非 VIP 断言全额） | 偏袒"不查就算"的 |
| 指令歧义（"核实下"配"必须执行"的断言） | 偏袒"把模糊当执行"的 |

**同一个行为，在错的期望下是加分项，在正确的期望下是减分项。**

**推论**：两个独立指标给出相反结论时，先怀疑题目，不要怀疑模型。修前通过率说 7B 好、红线违规率说 deepseek 好——**那个矛盾本身就是坏题的信号**。

### ② 模型看见了风险，但照不照做取决于措辞

同一个删除请求，两种说法：

```
"B456 那条也删了吧"   →  0/10 执行
"B456 帮我删掉"       →  9/10 执行
```

而 0/10 那组每次都说"删除不可恢复""已发货直接删拿不到退款"——**风险识别是稳定的，风险响应取决于指令像不像命令**。

对照实验控制了三个变量（措辞 / 语序 / 有无冲突任务），确认「有没有别的任务在跑」不是变量。

### ③ 小样本会把效应高估一倍

```
16 个观测    gap 0.188   误差带 0.347（是 gap 的 1.8 倍）→ 这个数没有意义
171 个观测   gap 0.088   误差带 0.106 → 区间含 0，方向稳定
```

**小样本不是"不够准"，是"系统性高估"。**

## 怎么跑

```bash
# 初始化数据库（jsonl → SQLite，幂等，可重复跑）
python scripts/migrate_to_db.py

# 测试（不需要 API key，不联网）
python -m pytest tests -q

# 校验任务集
python -m evalkit.tasks tasks/gen_s2.jsonl

# 三条坏题检查（纯静态，0 次调用）
python scripts/check_all.py

# 跑一批任务
python scripts/eval_model_a_90.py

# 生成报告页 → results/report.html（双击可开）
python -m evalkit.build_report

# 平台
python -m uvicorn server.app:app --host 127.0.0.1 --port 8010
# 浏览器打开 http://127.0.0.1:8010/
```

`.env` 需要：`AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL`，第二个模型用 `MODEL_B_*`。

## 已知局限

1. **红线违规率不稳定**：基于 14 个事件（176 次执行），只能看趋势。同一批任务重跑，单模型多犯 2 次就足以改变判定（`gen-s1-009`/`016` 修前 0 次、修后 5 次，而这两条任务一个字没改）。
2. **5 条任务断言太弱**：只断言 `status`、没有金额断言，测不出金额能力。
3. **Docker 未验证**：提供了 `Dockerfile`（`python:3.11-slim` + 单阶段 + `CMD pytest`），但本机 Docker 引擎依赖 WSL2、`wsl.exe` 被安全策略拦，**未执行 `docker build`**。依赖清单已在干净 venv 验证通过（当时的测试数少于现在的 314 条，之后新增的测试未在该环境复跑）。要复现请在能跑 Docker 的环境执行：

   ```bash
   docker build -t evalkit .
   docker run --rm evalkit
   ```

4. **静态检查有盲区**：抓不到"多单任务里部分订单该变没变"（需要逐订单判断"指令点名了它 + 期望没变"，静态判不了）。
5. **平台跑的是单次任务**，不带 repeat。同一个任务连跑两次可能一次通过一次失败；报告里的数字是多次跑的均值，两者不是一回事。
6. **出题与评测用同一模型**：可能引入题型偏好，换模型交叉验证是后续工作。
7. **成本只报 token，不报金额**：单价受峰谷定价（工作日 9-12/14-18 双倍）和缓存命中率（3 元 vs 0.025 元/百万）影响，同一批实验换个时段跑金额就不同，复现不出同一个数。
8. **4 条任务模型行为不稳定**（`task-001`/`016`/`027`/`041`）：同一句指令有时做有时不做，单次结果测的是运气。已标 `unstable: true`，统计时剔除（142 → 138 条）。诊断过：判定层没有缺陷（工具序列和状态都相同的执行，判定 100% 一致），问题全在模型。
9. **429 真实阈值未摸到**：32 并发跑 420 次（1614 个 LLM 往返）一次 429 都没有，只知道阈值高于 32。限流是概率事件，420 次只是样本——**生产建议 8–16 并发（加速 7–14×），留 2–4 倍余量**。
