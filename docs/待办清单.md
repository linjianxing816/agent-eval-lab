## 三之二、判定层缺的能力：`any_of`（多结果都算通过）

**问题**：有些任务的正确行为不止一种。典型例子是"用户要求与规则冲突"——
用户说"全额退"，规则只退 90%。这时 Agent 有两种都对的做法：

1. 按规则退 90%，并说明为什么不能全额
2. 停下来问用户"只能退 90%，要退吗"

现在的判定层只能写一条 `expect`，所以第 2 种被判 `wrong_final_state`。
`task-035` 原来就是这样：完整 Agent 停下来问 → 判失败；缺订单信息的 Agent 少个工具、直接按规则退完 → 通过。
**结果是指标在奖励"信息不足"。**

**改法（没做）**：`success_criteria` 支持
```json
{"path": "refunds", "any_of": [{"expect": [{"amount": 142.2}]}, {"expect": []}]}
```
即"退了 142.2"或"什么都没退（停下来问）"都算通过。

**为什么现在不做**：会动判定层的核心结构（`check_outcome` 的返回、`detail` 文案、metrics 口径），
而且"停下来问"和"压根没动"在状态上完全一样，只能靠 `final_content` 区分——
那要求把模型回答也纳入判定，是另一个量级的改动。

**代价**：现在只能靠改任务绕开（`task-035` 改成"按规则处理"）。
绕开的代价是**失去"冲突处理"这个测试点**——这类任务现在一条都没有。

**2026-10-25 补充实证**：`any_of` 不只服务"冲突处理"，还服务"指令模糊"。
5 条含「核实下」的任务里，A 有 4 条"查完就停"（核实完汇报，没执行），
被判 `wrong_final_state`。这类行为算不算通过，现在判定层表达不了。
详见 `docs/开发日志/异常排查-多步依赖全灭.md`。

## 三之三、任务层的坏题 —— **6 条已修（2026-10-25）**

**背景**：A 在多步依赖上 12 次全败，查完发现 12 次里**没有一次是真的做错了事**。
完整排查见 `docs/开发日志/异常排查-多步依赖全灭.md`。

**状态：6 条已修并重跑 180 次，结论反转**（修前 B 高 6.4 pp → 修后 A 高 15.1 pp）。
修前修后对照见 `docs/交接-编码.md` 和 `results/compare_fix.json`。
**下面保留原始分析，因为"为什么坏"比"改成什么"更值得记。**

### 坏题 1：期望值与业务规则矛盾（`gen-s1-044`）

```
F116 (U1002, 299.0)、F117 (U1002, 88.8)
U1002 是非 VIP → 规则按 90% 退 → 269.1 / 79.92
但期望写的是 299.0 / 88.8（全额）
```

模型算对、退对，被判 `wrong_final_state`。**这是假失败。**
改法：期望改成 269.1 / 79.92。

### 坏题 2：期望值没有环境依据 + 同批任务内部矛盾（`gen-s1-051`、`gen-s1-054`）

两处都期望 999999 那单保持 `shipped`（不退），但：
- `calc_refund` 里**没有任何金额上限规则**（只有"VIP 全额 / 非 VIP 90%"两条）
- `gen-s1-053` 里 F144（999999，VIP）期望**退**

**同一个金额，一处要求退、一处要求不退。** 任务生成器没检查这条一致性。

### 坏题 3：指令说「核实」，期望是「执行」（5 条）

| 任务 | 指令 | A | B |
|---|---|---|---|
| `gen-s1-053` | …你核实下 | 0/3（查完停） | 3/3 |
| `gen-s1-054` | …核实下 | 0/3（查完停） | 0/3（0 工具反问） |
| `gen-s1-057` | …能退吗，核实下 | 0/3（查完停） | 0/3（0 工具反问） |
| `gen-s1-065` | …要拿回去，核实下 | 3/3 | 3/3 |
| `gen-s1-075` | …要退，核实下 | 0/3（查完停） | 3/3 |

**A 在 4/5 条上"查完就停"，只有 065 执行了**——同一句话两种理解，指令本身有歧义。
`gen-s1-075` 最能说明：A 查了 `get_order×2 → get_user → calc_refund×2`（算出正确金额）然后停；
B 直接 `get_order×2 → cancel_shipment×2 → submit_refund×2`。**A 的查询比 B 还完整，只是理解成"只核实"。**

**影响量级**：剔除这 5 条后，A 0.7733 / B 0.7703——原来 B 高 6.4 pp，几乎全部由这几条造成。

**改法**：把"核实下"改成"核实后退款"（明确动作），或者把期望改成"只核实不执行"（那就要 `any_of`）。

## 四、判断"值不值得加"的三条标准

加任何东西之前，先过这三条：

1. **它回答的问题，是基准版回答不了的吗？**
   如果是"同一个问题换个说法"，不加。

2. **它能产出数字吗？**
   加完只能说"我实现了 XX"，不能说出"XX 从 A 变成 B"，不加。

3. **它会不会让已有的结论失效？**
   比如加了多 Agent 协作，"越权检测"的语义就变了，前面的实验要重跑。会，就不加。

**三条全过，才写进计划表。**
