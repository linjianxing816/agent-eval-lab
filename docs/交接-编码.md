## 二、TTFT 归因（10 次，去掉 6 个工具 schema）

| 场景 | 输入 token | TTFT P50（ms） |
|---|---|---|
| 带 6 个工具 schema | **846** | **795.3** |
| 不带 schema | 120 | **503.4** |
| 差 | +726 | **+292.0**（约 402 ms / 千 token） |

**prefill 占 37%、基线占 63%。** 既不是"prefill 占大头"也不是"缩短输入没用"——
缩短输入能省约 0.3 s，但省不到一半；真正的瓶颈是排队/连接。

**一处要纠正的前提**：你说的"带 schema 4,130 输入 token"是**单任务总 token**（5.6 步累加），
不是单次请求的输入。单次请求只有 **846** token（system prompt + 6 个工具 schema + 一句话）。
TTFT 只看单次请求的输入，所以对比要用 846 vs 120。

## 四、平台（D19 + D20 合并）

```
server/app.py            三个接口 + 一个页面
server/static/index.html 原生 HTML + fetch
```

| 接口 | 作用 |
|---|---|
| `GET /api/runs` | results/*.json 实验列表（8 个） |
| `GET /api/runs/{name}` | 单次实验详情（门禁 + 矩阵） |
| `POST /api/run` | 跑一条任务，同步返回轨迹 + 判定 |
| `GET /api/tasks` | 任务列表（选择器要用，比"三个接口"多这一个） |

**启动**：

```
.venv\Scripts\python.exe -m uvicorn server.app:app --host 127.0.0.1 --port 8010
```

浏览器打开 `http://127.0.0.1:8010/`。

**只做接线不做逻辑**：`run_task` + `judge_task` + `discriminate.AGENTS`，一行判定逻辑都没复制。
实验详情读 `results/report_data.json`（`build_report` 导出的），**不重新算一遍**——
重新算就意味着"报告里那个数"和"平台里那个数"是两份数据，迟早对不上。

`report_data.json` 导出时**去掉了 trajectories**（1.3 MB → 10 KB）：平台现场跑任务，不需要历史轨迹。

**实测**：
- `GET /api/runs` → 200，8 个实验
- `GET /api/runs/report_data` → 200，gate FAIL，4 行矩阵
- `POST /api/run {task-031, strong}` → 200，**1.3 秒**，1 步 `get_order`，判定通过
- `GET /` → 200，10,183 字节
