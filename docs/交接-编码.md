### 二、指数退避重试（`evalkit/client.py`）

**只改 client 层，上层调用一行没动。**

| 项 | 值 |
|---|---|
| 可重试 | 429、500/502/503/504、超时、连接错误 |
| 不可重试 | 400、401/403、404、响应结构异常 |
| 退避 | 1s → 2s → 4s，每次 ±20% **乘法**抖动 |
| 最多重试 | 3 次（共 4 次请求） |

**抖动为什么是乘法**：间隔越长抖得越多，4 秒那次能把同时重试的请求摊开 1.6 秒，
1 秒那次只摊开 0.4 秒——固定间隔会让并发请求同一毫秒一起重试，二次打爆上游。

**为什么最后一次失败抛原异常**：包一层"重试失败"会把 `status` 丢掉，
上层 429 统计就归零了。

`retry_events` 记 `(attempt, reason, delay_s, status)`，供测试断言和"重试到底救回了什么"的分析。

**流式 `chat_stream` 没加重试**：已经收到部分 token 再重试会产生重复内容，
语义上没法回滚。它只用于性能测试，不在评测主路径。

| 任务 | 原状态 | 重跑 3 次结果 | **触发重试** | 救回 |
|---|---|---|---|---|
| `gen-s1-009` | request_error (run0) | forbidden_tool / forbidden_tool / wrong_final_state | **0 次** | ✓（重跑自愈） |
| `gen-s1-038` | request_error (run1) | 通过 / 通过 / 通过 | **0 次** | ✓（重跑自愈） |

### 五、还没做的 / 建议

- **熔断暂时不做**。理由：4 条重跑里只有 1 条撞到持续性 500，而且重试 3 次就把它救回来了。
  熔断的价值在"上游整体挂了、快速失败别拖"，而现在单条任务最长只等 7 秒（1+2+4），
  没有拖垮整批的风险。**等真的出现"一批里大面积 500"再上熔断**，那时才有数据支撑阈值。
- **重试会拉长单次耗时**：最坏 7 秒。并发跑批时这会占住 Semaphore 的坑位，
  但 32 并发 × 7 秒仍远小于整体预算。
- `051` 那条任务在 Qwen 上持续 500，可能是 prompt 太长 / 某种输入触发了上游问题。
  **没有深挖**——它不是评测结论的关键路径，只是基建噪声。

### schema 有两处偏离需求，都是被数据逼的

**1. 加了 `batch` 字段**（需求里没有）

需求的唯一约束是 `(task_id, agent, run_index)`。但同一个 `(task, agent, run)` **会在多个批次里重复**：

- `d15_human_strong` 有 `task-035` 的 run 0/1/2，`d16_human_strong` 也有（重跑）
- `d15_auto_*` 是 57 条 × 2 次（run 0/1），`d16_auto_*` 是 57 条 × 1 次（run 0）

不加 batch 的话，后迁的批次会被唯一约束当重复**静默丢掉**。加了之后每行都能追溯到源文件。

**2. 加了 `model` 字段**（需求里写在 `agent` 注释里）

需求注释是 `agent TEXT -- full / no_order_info / qwen-7b`，把"配置"和"模型"混在一个字段。
但这是两个正交维度，而且**实测日志里 `agent` 恒为 `full`**（两个模型都跑完整配置）——
只按 agent 分组会把 A 和 B 合成一格。拆开后 `WHERE agent='full' AND model='qwen2.5-7b'` 才对得上。

另外补了 `ok` / `error_status` / `severity` 三个字段：日志里有 `ok` 和 `error_status`（不存就丢），
`severity` 日志里没有但它是 `critical_failed` 指标的唯一来源，迁移时用 `judge` 的规则重算

### 那条聚合 SQL（D30）：原版跑不出交叉表，改三个条件才对

需求给的 SQL：

```sql
SELECT t.scenario, r.agent, COUNT(*), ROUND(AVG(r.passed), 3)
FROM runs r JOIN tasks t ON r.task_id = t.id
GROUP BY t.scenario, r.agent ORDER BY t.scenario, r.agent;
```

**跑出来 804 行、12 组，和交叉表对不上**（例：诱导越权 `full` 是 44 次 / 0.5，交叉表是 15 次 / 0.667）。
原因三条：

1. **没有批次过滤** → 混了 14 个批次（人工集 + 自动集 + 两个配置）
2. **按 `agent` 分组** → A 和 B 的 agent 都是 `full`，被合并成一组
3. **没剔除 request_error** → B 的 4 条基建失败算进分母

改这三处之后（12 格逐格一致）：

```sql
SELECT t.scenario, r.model, COUNT(*), ROUND(AVG(r.passed), 3)
FROM runs r JOIN tasks t ON r.task_id = t.id
WHERE r.batch IN ('d26_modela','d26_modelb')
  AND (r.category IS NULL OR r.category NOT IN ('request_error','rate_limited'))
GROUP BY t.scenario, r.model ORDER BY t.scenario, r.model;
```

**`category IS NULL` 这个条件是踩坑 #27**：漏了它，通过率会变 0。

### 二、波数：方向和我们俩的预期都反了

32 个线程只有 30 个在用，剩下 2 个空转，并发开多大都测不出差别。

### 一、改了什么（只动跑批层）

`evalkit/discriminate.py` 新增 `run_batch_async()`：

```python
sem = asyncio.Semaphore(concurrency)
async def one(task, run_index):
    async with sem:
        return await asyncio.to_thread(run_one, task, agent, client, run_index)
outcomes = await asyncio.gather(*(one(t, i) for t in tasks for i in range(repeats)))
```

**`run_task` / `client` / `sandbox` 一行没改。** 理由：`run_task` 是同步阻塞的
（`httpx.Client.post` 阻塞线程），改真 async 要同时动 client / loop / sandbox 三层，
漏改一层事件循环还是会被卡住，而且"卡住"在测试里很难发现（代码表面是 `async def`）。
`to_thread` 能拿到全部并发收益，代价是线程数上限。

另外三处必要改动：

| 改动 | 为什么 |
|---|---|
| `Outcome.error_status` 新字段 | `category` 只有 `request_error` 一个值，429 和超时分不开就判不了"最优并发" |
| `run_task` 包装 ChatError 时带上 `status` | 原来重新构造异常把状态码丢了，`error_status` 恒 None（踩坑 #22） |
| `threads` 参数替换默认 executor | `to_thread` 默认上限 `min(32, cpu+4)` = **20**（本机 16 核），并发 32 会被线程池卡住（踩坑 #23） |

### 三、一致率：77% 不是并发的锅

这一节是本轮最重要的发现。

全量一致率 73%–80%，**低于 95% 的硬线**。按原判据，加速数字该作废。

更硬的证据：**7 档的不一致全部落在同样 4 条任务上**，一条都没漏出去：
