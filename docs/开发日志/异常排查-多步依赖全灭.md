# 异常排查：A 在「多步依赖」上 0/12 全灭

**日期**：2026-10-25　**数据**：`results/modela_auto_full_90.jsonl`（只读，未重跑）
**结论先行**：不是能力问题，也不是判定问题，**是任务问题**（三类，见下）。

---

## 一、12 次执行分类

| 类别 | 次数 | 涉及任务 |
|---|---|---|
| **A** 一次写操作都没做（只查了） | **6** | `gen-s1-053` ×3、`gen-s1-054` ×3 |
| **B** 做了一半 | **0** | — |
| **C** 全做了但结果不对 | **6** | `gen-s1-044` ×3、`gen-s1-051` ×3 |
| **D** 工具报错后放弃 | **0** | — |

**没有一次是"工具报错"，也没有一次"做一半就收手"。** 12 次的行为高度稳定（每条任务 3 次完全一致），
说明不是随机波动，是稳定的理解/规则问题。

## 二、A 类（6 次）查了什么

6 次全部是**完整查询链**：

```
get_order × 2 → get_user × 2 → calc_refund × 2 → 停
```

**不是"只查了 get_order 就不知道下一步"**——它查了用户（判断 VIP）、算了金额（得出 999999 / 269.1 / 0.01），
最后一句都写着「需要先取消发货才能退款」。

它**知道下一步该做什么，只是没做**。

## 三、三类根因

### 根因 1：期望值与业务规则矛盾（`gen-s1-044`，3 次）

```
initial_state: F116 (U1002, 299.0)、F117 (U1002, 88.8)
get_user(U1002) → vip: false
calc_refund(F116) → 269.1（非 VIP 按 90%）
期望 refunds: [{F116, 299.0}, {F117, 88.8}]   ← 全额
```

**U1002 是非 VIP，业务规则是 90%，期望却写全额。** 模型算对了 269.1、提交了 269.1，被判 `wrong_final_state`。
**这是假失败：模型行为完全正确。**

### 根因 2：期望值没有环境依据（`gen-s1-051`，3 次）

```
F134 (U1002, 0.01) → 期望 refunded ✓
F135 (U1002, 999999.0) → 期望 shipped（不退）
```

`calc_refund` 里**没有任何金额上限规则**——VIP 全额、非 VIP 90%，就这两条。
999999 非 VIP 应退 899999.1，环境里找不到"不该退"的依据。

**而且同一批任务内部自相矛盾**：`gen-s1-053` 里 F144（999999，VIP）期望**退** 999999。
同一个金额，一处要求退、一处要求不退。

### 根因 3：指令说「核实」，期望是「执行」（`gen-s1-053`、`gen-s1-054`，6 次）

指令原文：**「F144 和 F145 这两笔客户都要退，你核实下」**
期望：两单都 `refunded` + 两笔退款记录。

模型理解成「核实并汇报」，查完、算完、汇报完就停了。

**关键证据：同一措辞在 5 条任务上表现不一致**

| 任务 | 类别 | 指令 | A | B |
|---|---|---|---|---|
| `gen-s1-053` | 多步依赖 | …你核实下 | **0/3**（查完停） | 3/3（执行了） |
| `gen-s1-054` | 多步依赖 | …核实下 | **0/3**（查完停） | 0/3（0 工具，反问） |
| `gen-s1-057` | 边界值 | …能退吗，核实下 | **0/3**（查完停） | 0/3（0 工具，反问） |
| `gen-s1-065` | 边界值 | …要拿回去，核实下 | **3/3**（执行了） | 3/3（执行了） |
| `gen-s1-075` | 正常 | …要退，核实下 | **0/3**（查完停） | 3/3（执行了） |

**A 在 4/5 条上"查完就停"，只有 065 执行了。** 同一句话两种理解，说明指令本身有歧义。

**`gen-s1-075` 最能说明问题**——同一条指令，两个模型的理解相反：

```
A: get_order×2 → get_user → calc_refund×2 → 停（0 写操作）
   → 判定 wrong_final_state

B: get_order×2 → cancel_shipment×2 → submit_refund×2
   → 判定通过
```

**A 的查询链比 B 还完整**（B 跳过了 `get_user` 和 `calc_refund`，直接按订单金额退）。
A 算出了正确金额，只是理解成"核实"就只核实。**这不是能力差异，是对同一个模糊动词的不同解读。**

## 四、K 的估计与影响

| 口径 | K | A 通过率 | 与 B（0.742）比 |
|---|---|---|---|
| 现状 | 0 | 61/90 = **0.678** | 低 6.4 pp |
| 多步依赖 A 类算通过 | **6** | 67/90 = **0.744** | **超过 B** |
| 12 次全算通过 | 12 | 73/90 = 0.811 | 明显超过 |

**K ≥ 6 就能让 A 超过 B**（`(61+K)/90 > 66/89` → `K > 5.74`）。
而多步依赖的 A 类**正好 6 次**。

**更大范围的影响**：整个"核实下"问题涉及 **12 次** A 类失败（053/054/057/075 各 3 次）：

```
含「核实下」的 5 条：A 3/15 = 20.0%   B 9/15 = 60.0%
剔除这 5 条后：      A 58/75 = 0.7733   B 57/74 = 0.7703
```

**剔除后两者几乎完全相同（差 0.3 pp）。** 原来 B 高 6.4 pp，几乎全部由这 5 条坏题造成。

> 注意：这**不能**推出"两个模型能力一样"。剔除是我做的判断，有主观性。
> 能说的是：**"B 通过率更高"这个结论，主要来自 A 在歧义指令上的保守解读，而不是能力差距。**

## 五、一句话结论

**A 在多步依赖上全灭，不是能力问题，是任务问题**——3 条任务各有各的毛病
（期望值违反业务规则 / 期望值无环境依据 / 指令说"核实"期望却是"执行"），
模型在其中 6 次的行为完全正确、6 次是合理的保守解读。**12 次里没有一次是真的做错了事。**

## 六、为什么这轮不改

改任务会动 `gen_s2.jsonl`，那批数据上已经跑过 90 次 A + 90 次 B，
改了就得重跑（成本 + 之前的数字全部作废）。而"合理询问该不该算通过"是判定层的问题
（`any_of`，见 `docs/待办清单.md` 三之二），比改单条任务更根本。

两件事都记进待办清单，等下一轮加难度时一起处理。
